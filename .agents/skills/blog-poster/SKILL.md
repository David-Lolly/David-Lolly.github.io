# 博客与项目发布

## 操作边界

- 文章中的 Markdown、MDX、Mermaid 语法错误可以直接修复；保持原意的图表排版修正也可直接处理。涉及正文观点、技术含义的改变先与用户同步。
- 如果问题需要修改站点源码（组件、全局样式、主题逻辑、构建配置、依赖等），先反馈问题现象、原因、拟修复方案及影响范围，获得确认后再修改。发布指令本身不代表授权修改站点源码；已有明确授权无需重复确认。
- 不逐步骤索要确认。仓库或上下文能确定的信息自行核对；确实需要用户决定的问题集中询问。
- 本流程中的生产构建仅在用户要求推送时执行。仅整理、预览或提交，不运行生产构建。
- “提交”只授权本地 commit；“推送”“发布到远程”等明确指令才授权 push。保留会话中已有的明确授权，不重复询问。

## 1. 整理内容和资源

先检查工作区、目标文章是否已存在，以及 `velite.config.ts` 的当前 schema，避免覆盖无关改动或重复创建文章。

- 博客：`content/blog/{slug}/index.mdx`；项目：`content/projects/{slug}/index.mdx`；资源放各自的 `images/`。
- 接受纯 Markdown 或已有 frontmatter 的 MD/MDX。类型已明确时不再询问；新文章生成必要元数据，已有文章保留日期与 slug，除非用户要求改变。
- 当前必需字段是 `title`、`slug`、`date`；博客可选 `image`、`description`、`categories`、`featured`；项目还支持 `status`、`tags`、`github_url`、`demo_url`、`stars`、`forks`。以实际 schema 为准。
- 日期使用用户时区；新文章未指定日期时使用当天。不得为通过校验而编造项目链接或资源路径。
- 保留正文含义和代码示例。没有语言标记的代码块依据内容判断，无法判断时保留纯文本，不统一标成 C。
- 检查疑似凭据、内部地址和个人信息；明确的真实秘密作脱敏处理并简述，含义不明确时询问，不将所有路径或内网示例机械替换。
- 校验本地图片存在、引用正确、扩展名与格式一致。无封面时省略可选 `image` 字段，使用站点已有占位行为，不引用不存在的文件。
- 有封面时读取实际宽高，避免拉伸。优先复用用户图片；不能仅因比例不同就擅自裁掉内容。列表当前采用固定高度与 `object-cover`，须在实际卡片中确认裁切后主体、文字完整；项目详情当前为 16:9，博客详情不自动展示封面。不要把某一历史图片尺寸作为通用硬性要求。

## 2. Markdown 与 Mermaid 检查

检查代码围栏、MDX 特殊字符、图片及内部链接。枚举本次新增或修改文章的全部 Mermaid 代码块，确保每张都有验收结果。

已知风险只作排查线索，不代替渲染证据：

- 子图标题避免 `<br/>` 换行；单行分隔可以保留完整含义。
- `%%{init: ...}%%` 如需使用，放在图定义首行；不无故覆盖组件默认配置，不使用无效配置键。
- 过小的 `rankSpacing` 可能造成子图标题压住节点。当前组件默认 36，历史实测单节点子图仍可能重叠；该类图局部设置 52 曾得到 5px 间距。不要将这些数值当作所有图的安全保证。
- `direction` 与 `diagramPadding` 曾无法解决该标题间距问题，不应反复试用替代真实测量。
- `mermaid.parse()` 只能辅助语法检查；构建成功也不能证明图表显示正确。

## 3. 使用真实页面预览验收

先查看是否已有本项目可用的开发服务；优先复用，不能重复占用端口。需要启动时运行 `npm run dev`，记录端口、进程或工具会话 ID 和所有权。文章 URL 带结尾 `/`。

由 agent 使用浏览器工具打开真实文章页，等待所有图渲染完成，逐图截图并目视检查：

- Mermaid 数量与文章代码块一致，无加载残留或渲染失败。
- 子图标题、节点文字、连线标签完整，无重叠、遮挡或裁切；连线端点关系正确。需要时测量标题与节点间距、节点矩形重叠，不能仅凭 DOM 元素存在认定通过。
- 检查明暗主题及桌面、窄屏；切换主题时阅读位置、图表高度与已有缩放不应意外变化。
- 同时检查标题、列表、引用、代码块、正文图片及列表封面的实际显示。

按操作边界处理发现的问题，修复后复查受影响部分。无法使用浏览器或存在未解决问题时，明确记录未验证范围，不宣称“验收通过”。

给用户提供实际预览地址、改动摘要和验证结果，供其亲自查看。用户仍在查看时临时保留本次预览服务；用户确认结束、转入其他工作或本次发布完成后，停止自己启动的服务，除非用户明确要求保留。不得在任务结束后无限期留在后台。

仅停止本次创建且身份已核实的进程或工具会话；不要按进程名批量结束 Node，也不要擅自停止用户或其他任务启动的服务。复用的服务报告其归属，需关闭时先与用户同步。服务退出后检查监听端口，报告是否已释放。

## 4. 用户要求推送时的最后检查

收到推送授权后，才执行以下步骤：

1. 确认待推送范围经过前面的预览检查；存在未验收内容时先完成预览检查，不能把浏览器验收省略掉。
2. 停止自己启动且仍运行的预览服务，再运行 `npm run build`。现有脚本依次执行 Velite 与 Next.js 静态构建，并生成搜索索引及静态资源。
3. 必须等待明确成功退出。失败、卡住、中止都不是成功：查看输出并定位原因；文章语法问题直接修复重试，涉及站点源码时按操作边界反馈。不能绕过失败推送。
4. 构建成功后不再打开浏览器，也不要求用户重复预览；检查生成文件与 Git diff。当前为静态导出 `out/`，不要使用 `next start` 验证。
5. 明确指定本次内容、对应生成文件及已授权改动进行暂存，排除截图、浏览器日志、临时校验目录和无关图片。遵循仓库中文 Conventional Commits，正文仅记录实际执行的验证。已提交内容不重复提交；构建产生的必要变更追加正常提交，不擅自改写历史。
6. 执行授权的 push，检查结果。报告提交、分支和推送状态；推送 main 会触发 `.github/workflows/deploy.yml` 构建并部署 GitHub Pages，推送成功不等于部署成功。没有检查 Actions 时明确尚未确认部署。
7. 完成后再次检查本次启动的服务是否已停止。需要更新的产物为整站静态输出 `out/`，由现有 Actions 生成部署；本仓库无需容器镜像更新。

若用户只要求本地提交，沿用已完成的预览证据提交，不提前运行生产构建，不推送。
